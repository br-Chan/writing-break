TanStack Query

Day 2 of my full-stack web project: figure out how to set up TanStack Query.

I’ve had cursory experience with the library, limited to writing up query & mutation hooks (and watching the query client code in respectful awe). I spent a day learning and researching. Most of this wasn’t to do with rote learning how TanStack Query works (something I already knew), but instead with the best way to set it up and achieve what I wanted in a well structured manner. I took a look at Bulletproof React, my go-to for all things architectural, as well as existing repositories I’ve contributed to that use TanStack Query. I could say more about Bulletproof React, but for now here’s what they say about isolating the API layer.

I created a single instance of my API client using Axios. This way, I can configure it however I want and use it across the whole application, reducing many headaches. It’s also fun to be able to import the api client from a cool and spooky location and go api.get() in one swift call… No? Just me?

The TL;DR of TanStack Query is you create a new QueryClient (courtesy of the library) and use a QueryClientProvider to wrap your application in main.ts. Then you can call special hooks to make queries.

I also did a funky thing with a function called createRootRouteWithContext. It does exactly what it says on the tin, creating the route such that it requires a certain context to be given to it – in my case, the query client. This root context will be provided to all routes in the route tree without having to provide it to each route individually. To be completely frank, I don’t yet fully grasp the utility of providing the query client to each route if I’m going to be defining the API requests externally. My thinking is that this isn’t as useful in the way I’ve decided to structure my project, but perhaps I just haven’t grasped the idea fully in the first place.

My time at WDCC exposed me to the wonderful design pattern of defining API requests separately. That, paired with Bulletproof React’s “features” guidelines makes for a very juicy architectural combination. More on that later.

: Speaking of WDCC…

In our project last year, our API client was completely hand rolled by our resident web dev pro. It was 473 lines long… I don’t know how to feel about that. In my honest opinion, it’s not a bad thing to reduce bloat in your own application by using a trusted, well-used dependency.

OpenAPI TypeScript

Moving onto day 3…

During my research, I had a growing concern: how should I keep types in the frontend synchronised with the backend? Without manually writing them in both the frontend and backend, that is (which would be an utter pain and kick me out of the software engineering space).

In my internship, the answer to that was to create a shared package as a yarn workspace and add it as a dependency in the package.json. I immediately flashbacked to all the horrors of trying to get the type safety working properly… Never again. At least, not with yarn.

Meanwhile, Bulletproof React’s demo repo has a types/api.ts file that says:

// let’s imagine this file is autogenerated from the backend

Bingo.

Let’s auto-generate the file from the backend

My research led me to openapi-typescript, a library that converts OpenAPI schemas to TypeScript types. This fit perfectly because ASP.NET recently updated themselves to use OpenAPI by default, so I’ve basically got everything set up already. I dove into openapi-typescript research.

The process is as follows:

  1. Obtain your input OpenAPI schema (JSON or YAML).
  2. Run the openapi-typescript command to convert the schema file to an output .ts file.
  3. Use this .ts file to your heart’s content.

I may be explaining my dev work out of chronological order a bit, but I ended up writing a package.json script called gen-api to automate all this. Firstly, I installed a backend package that outputs the OpenAPI schema in the output obj folder whenever the build runs. Then:

"gen-api": "dotnet build apps/Backend && pnpx openapi-typescript apps/Backend/obj/Backend.json --output apps/Frontend/src/types/api.ts",

So whenever I make changes to the backend, I just need to run pnpm gen-api and the updated schema is channelled into the api.ts. This will also help when I set up CI/CD and deploy this application in the murky future. I’m quite chuffed with this workflow, though!

The auto-generated file

For curiosity’s sake, here’s the skinny on the file generated by openapi-typescript.

The paths interface exposes the whole API. For example, “/api/Friends” has a get and a post, but no put or delete. Each post request has no parameters but does have a request body, and has a response of status 200 with certain expected content. All of that is described by the paths interface.

The components interface contains all your schemas. My Friend model written in C# is here.

These are meant to be exported and used to create your frontend types. For example:

export type Friend = components["schemas"]["Friend"];

It may look stupid, but it’s comforting to know that you have a single source of truth in the backend, and that the Friend type is 100% accurate. I really enjoy it being “data-driven”, or if that’s the wrong term, the idea that you only need to change one thing and everything else follows suit. It’s something that developers like Mojang are doing in Minecraft, making everything under the sun data-driven (from configuring blocks that are flammable to what is a painting). My writing blog is also data-driven in a way: I simply need to add a markdown file and everything else is handled for me to display it in the UI. It’s a very simple kind of beauty.

OpenAPI Fetch

The people who made openapi-typescript also made openapi-fetch, a “type-safe fetch client that pulls in your OpenAPI schema. Weighs 6 kb and has virtually zero runtime”. I found this really rewarding, even though I had to switch out Axios for it.

Notice how I pass in paths from the auto-generated api.ts as a generic in createClient. That’s important for enabling type-safety!

Other than some differences in syntax, the API client is essentially the same! But now it’s TYPE-SAFE. As someone who suffers from chronic carelessness, getting type errors and intellisense for entire APIs is like ambrosia.

Services and Hooks

It was finally time to write up my services and query hooks.

Bulletproof React promotes the idea of organising code into feature folders. You can read more about project structure here. In my project, I created a src/features/friends directory and an api folder within to house my service.ts and queries.ts. I find this method of organisation pretty neat, because it keeps everything modular and separated really intelligently (as long as you do it right).

Bulletproof React also promotes a very uni-directional flow of dependencies between code, which I’ve used to great effect in my most recent internship and in a couple personal projects. I won’t go too into it, as the link above discusses it more than well enough. I look back fondly on the lengthy discussions with my internship partner Joran as we figured out how to structure a legacy codebase into something much more palatable.

There seem to be a couple different ways to write your frontend services, but I go for the following strategy:

const FriendService = {
    createFriend: async (data: FriendCreateRequest) => {
		const response = await api.POST("/api/Friends", {
			body: data,
		});
		return response;
	},

	getFriends: async () => {
		const response = await api.GET("/api/Friends");
		return response;
	},

	getFriendById: async (friendId: string) => {
		const response = await api.GET(`/api/Friends/{id}`, {
			params: { path: { id: friendId } },
		});
		return response;
	},

    // And so on...
}

Then you refer to each service function like FriendService.getFriends. Note the interesting OpenAPI Fetch syntax.

This way differs from what Bulletproof React suggests, in which each action is put in its own file (e.g. get-friends.ts, create-friend.ts, etc.). I decided to go for a proper service ‘layer’, followed by a single queries file.

The above is pretty bread and butter for TanStack Query. You create a query or mutation hook and use either useQuery or useMutation depending on if you’re fetching data or manipulating it in some way.

I created a shared friendsQueryOptions function so that I could write the query key in just one place, and use it when invalidating queries in the useCreateFriend mutation hook. Query invalidation is a thing you need to do because once you manipulate certain data, you need to “invalidate” out-of-date data that may be cached from previous queries.

I could create a “query key factory” or something like that – it was something I read up on. I’ll look into it at some point, but when I only have one query key to keep track of (“friends”) I don’t see the utility just yet.

While I was doing this, I took the time to create DTOs for the Friend model: FriendCreateRequest and FriendUpdateRequest. They’re both identical, just without the id field since there is no need for the user to give an id when creating or updating a certain friend. Because of my clever workflow design decisions made earlier in the day, all I had to do was write up the C# classes, update the controller functions to use these Request models, and then run pnpm gen-api to update the frontend api.ts!

Now I needed to make sure that the changes I’d made to the backend weren’t breaking anything, but so far I hadn’t anything to interact with the API.

Swagger vs. Scalar

Swagger is the de facto interactive OpenAPI documentation. I’ve had experience using it before to test APIs.

But I found out that OpenAPI had an update and recently moved to this other thing called Scalar UI to replace Swagger as the default. Or maybe I read it wrong, and OpenAPI simply never shipped with built-in support for Swagger. Either way, here’s the specific Microsoft Learn article talking all about it.

I originally had a Swagger set up, but I was having a conflict with the schema where the Swagger wouldn’t perceive me entering values into the input fields and gave me validation errors even though I followed them to the letter. So I went with Scalar, the prescribed modern alternative.

I was VERY skeptical – I always err on the side of caution when introducing myself to new techs for little reason. But I was blown away by how suave Scalar looks:

It completely does away with the tacky 2010s design of Swagger and goes for a more modern, minimal look. And, vitally, it still provides request testing. It lets you set the cookie, header values, and of course the query params and request body with a very intuitive UI/UX.

I’m quite happy to be using Scalar now. I’ll see how it goes. I made sure all my endpoints worked fine with the new models.

Can we actually see something happen now?

Up to this point, I still don’t know if there are any bugs in fetching data from the backend and if I’ve written any TanStack code wrong.

Meanwhile, while writing up this post, I noticed another openapi-typescript library I hadn’t noticed before: openapi-react-query. It’s apparently a thin library made precisely for my situation: using TanStack Query with openapi-typescript and openapi-fetch.

Oh god, I thought, I really shouldn’t get myself lost in this type-safe rabbit hole.

Right?

That, as well as actually seeing if this whole architecture works, will be the agenda for the next post.
